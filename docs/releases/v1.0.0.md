# v1.0.0

Implementation compatibility notes. No release has been published by this change.

## Database compatibility

Supports schema 4 through 10; current schema 10. Sequential transactional migrations preserve existing encrypted credentials, named keys, benchmark observations, usage counters and Codex identity. New tables store settings/revisions, administrator session hashes, operator budgets/reservations/totals and bounded activity metadata. Schema 10 adds hashed, expiring, single-use administrator password-reset records. Schemas 1–3 require the documented explicit baseline reset; unsupported newer schemas are rejected. The existing database master key must be retained.

## Configuration changes

Normal startup and management use SQLite settings. Before upgrading a YAML installation, explicitly run `gateway config import --config PATH --database PATH` with the original database and key. Import refuses established database settings and atomically imports settings and submitted secrets; catalog files become inline overrides. `serve`, provider auth, administrator, credential, benchmark and model commands use `--database` rather than `--config`. `serve --listen` and `TORII_LISTEN` are bootstrap overrides. YAML validation/import remain available. Optional certificate files remain external resources.

Console settings save automatically; provider Add/Edit saves on confirmation. New settings include seven-day persistent cookie sessions and trusted proxy networks, provider-qualified model enablement, native Ollama free-model defaults, disabled-by-default per-key/gateway budgets and bounded metadata activity/logging. Administrator username/email/password updates require current-password reauthentication and revoke cookie sessions/reset links. Optional email password recovery requires a saved recovery address and the HTTPS/SMTP runtime settings documented in [Environment](../reference/environment.md#password-reset-email-delivery). Inference Bearer keys and administrator Basic automation remain supported. Quota costs are estimates for operator accounting, not provider billing.

## Upgrade prerequisites

Stop gracefully, archive the complete database directory/volume and legacy configuration, back up the original master key separately and retain the previous binary/image. Build or select a verified pinned artifact, explicitly import legacy configuration before normal startup, then recreate with the original volume/key and listener options. Keep certificate paths readable by the non-root user. Verify health, discovery, administrator sessions, JSON/SSE inference, saves and budgets before retiring the rollback backup. See [Backup and upgrade](../guides/backup-and-upgrade.md).

## Rollback

Stop the new version and restore the complete pre-upgrade stopped database and legacy configuration with their original master key and retained application image/binary. There is no schema downgrade. Changes, reservations, sessions, key revocations and activity after the backup are lost; restoring old key records can reactivate revoked keys. Retain and protect the backup until verification is complete.
